# 腾讯云轻量 4核4G3M 抢购助手方案

状态日期：2026-10-28
用途：技术方案评审，不构成购买成功保证
实现位置：`tools/tencent_purchase/`

> 当前实现状态（2026-10-30）：纯 UI 链路和页面内高频 `fetch` 均已实盘失败。
> 用户随后要求继续降低网页运行时开销；当前定时任务改为独立 Python HTTP/2
> 客户端下单。Edge 仅用于加载登录态、在进程内存中读取 Cookie 和执行当前签名函数。
> 仅上海、有界提交、手动付款等安全边界保持不变。
> 第 20 节是当前权威设计；
> 第 7–19 节的配置弹窗、跨域确认页和 `.submit-btn` 流程保留为历史记录，
> 不再是定时任务的提交路径。

## 1. 目标与边界

目标是在用户控制的 Windows 电脑上，通过 Playwright 驱动一个已登录的腾讯云专用
Edge 配置，在指定秒杀窗口内尝试购买：

```text
日常大促-秒杀-轻量 4核4G3M
```

脚本在 14:59:58.5 至 15:00:30 的有界窗口内分批尝试创建未支付订单，取得订单标识后立即
停止并通知用户。高频尝试可能产生多笔未支付订单，由用户检查并逐笔取消。是否付款
由用户拿手机手动完成。

明确不做：

- 不自动付款、不调用支付接口、不保存支付凭据。
- 不使用多账号、并发运行或分布式抢购。
- 不绕过登录、验证码、实名认证、排队、风控或限购。
- 仅在同一个已登录浏览器上下文中复用当前活动页的 CSRF、请求头和动态签名，
  直接调用当前活动的库存及下单接口；不导出 Cookie，不复制第三方旧请求。
- 直接接口只允许上海一个地域，不使用多账号或跨地域并发。
- 14:59:58.5 开始发送；每批最多 10 个并发，批间等待 350–600ms 抖动；
  收到 408 后下一批延后 1.5 秒；15:00:30 硬停止，总请求上限 200。
- 取得订单标识后立即停止新增提交。
- 遇到验证码、实名要求、排队或平台风控时停止，不绕过。

## 3. 为什么明显不是“保证买到”

用户观察到商品约 1 秒售罄。UI 自动化的关键路径包括：

1. 活动页等待 CTA 变为“立即抢购”。
2. 第一次点击 CTA，腾讯云请求并生成配置上下文。
3. 配置弹窗完成加载。
4. 选择地域、镜像并确认价格。
5. 点击弹窗购买按钮，进入跨域订单确认页。
6. 校验商品、配置、数量和金额。
7. 点击一次 `.submit-btn` 提交订单生成请求。
8. 腾讯云服务端确认库存和资格。

库存只在最后服务端请求中确认，脚本无法提前锁库存。因此目标只能是：

> 在不违规、不重复下单和绝不付款的前提下，尽可能缩短本地等待与操作延迟。

## 5. 运行环境

- 运行主机：用户控制的 Windows 电脑。
- 浏览器：已安装的 Microsoft Edge。
- 浏览器配置：专用自动化 profile，不使用日常浏览 profile。
- Python：Windows 独立虚拟环境，不污染系统 Python。
- 凭据：PushPlus token 使用 Windows DPAPI 保存，不在命令行、日志、仓库或记忆中
  保存明文。
- 电源：接通交流电时禁用睡眠、休眠和合盖休眠（硬件不支持时会警告）。
- 唤醒：任务启用 `WakeToRun`，若处于支持的可唤醒状态可提前唤醒。
- 用户会话：任务注册为当前用户交互会话；Windows 必须已登录，锁屏允许。
- 网络：任务不主动提供网络兜底，网络不可用时失败关闭。


- DOM 监听不增加腾讯云网络请求。
- 最多点击目标 CTA 一次。

## 8. 购买配置策略

### 8.1 地域

为降低热点路径延迟：

1. 如果弹窗默认地域已选中，且是上海、北京、广州之一，并且没有售罄标记，
   直接使用默认地域。
2. 默认地域不可用时才按以下顺序回退：

```text
北京 -> 上海 -> 广州
```

### 8.2 镜像、时长、数量

- 镜像：Linux；Windows 不匹配时停止。
- 时长：1 年；其他值停止。
- 数量：1 台；其他值停止。
- 总金额：38.00 元；其他值停止。

### 8.3 自动续费

- 不在购买关键路径上处理自动续费开关，避免增加点击和等待。
- 付款后用户应到轻量应用服务器控制台核实并关闭自动续费。
- 脚本不得声称自动续费已经关闭，除非运行时证据明确证明。

## 9. 完整购买流程

### 9.1 预检

- 打开活动页并确认登录态。
- 定位唯一的精确目标卡。
- 校验商品名、SKU、流量、活动价、原价。
- 等待价格从“价格查询中”变为完整值。
- 目标卡异常、多个匹配或价格不符则停止。

### 9.2 等待 CTA

- 在页面内安装单个 `MutationObserver`。
- 只在当前 `#MS` 内查找唯一目标卡。
- 当 CTA 变为可用的“立即抢购”且价格已加载时返回。
- “已抢光/已结束”视为本场不可购买。
- 超时仍未见可购买状态则保存截图和 DOM 后停止。

### 9.3 打开配置弹窗

- 点击 CTA 一次。
- 等待包含目标商品和配置字段的单个可见对话框。
- 读取一次控件结构，作为运行时取证。
- 只接受当前目标商品的唯一配置弹窗。

### 9.4 选择配置

- 默认可售地域优先。
- 默认售罄时才切换候选地域。
- Linux 必须是已选状态或可以成功选中。
- 再次核对 1 年、数量 1、38 元。
- 若出现购买前服务协议，只勾选明确的腾讯云服务协议。
- 点击配置弹窗中唯一的“立即抢购/立即购买/确认购买”按钮。

### 9.5 跨域订单确认页

- 允许腾讯云自己弹出新页面。
- 检测到订单确认页后关闭原活动页，只保留一个订单页面。
- 等待标题/页面进入“确认产品信息”。
- 核对目标商品、配置、地域、时长、数量。
- 优读取 `.submit-info .price`，要求实付金额等于 38.00 元。
- 不匹配则不点击订单生成。

### 9.6 最多一次订单生成

- 找到唯一的 `button.submit-btn`。
- 初始文本必须为“去支付”或明确等价的下单前文本。
- 若文本已经是“确认支付/下一步”，说明已处于支付阶段：
  - 不点击；
  - 记录为已创建未支付订单或未知状态；
  - 通知用户。
- 点击前持久化 `submit_attempted=true` 和 `submit_intent_at`。
- 点击调用返回后写入 `click_returned_at`。
- 明确观察到支付阶段后写入 `payment_stage_at`。
- 只点击一次 `.submit-btn`。

### 9.7 结果判定

点击后最多等待 10 秒：

- 明确进入“支付订单”或出现“订单提交成功，待支付”：
  - 结论：未支付订单已创建；
  - 不点击“确认支付”；
  - 发送 PushPlus；
  - 结束当天剩余场次。
- 明确出现“订单提交失败/下单失败/商品已售罄”等结论：
  - 没有进入订单生成；
  - 上午场可保留下午场；
  - 下午场结束后不再尝试。
- 网络中断、页面空白或状态不明确：
  - 结论：`UNKNOWN`；
  - 不刷新、不重试、不运行当天另一场；
  - 保存截图和 DOM；
  - 通知用户检查订单管理。

## 10. 状态机

```text
EMPTY
  |
  | 开始某场
  v
SESSION_ATTEMPTED
  |
  +---- 登录/配置/价格等硬校验失败 ----> HALTED_TODAY
  |
  +---- 售罄/目标卡暂缺，未提交 -------> RETRYABLE_FAILURE
  |                                              |
  |                                              +--> 当天另一场可执行
  |
  +---- 点击 .submit-btn 一次
                         |
                         +---- 明确支付阶段 ----> ORDER_CREATED
                         |
                         +---- 明确失败 --------> RETRYABLE_FAILURE
                         |
                         +---- 10 秒不明确 ----> UNKNOWN
```

持久化状态字段：

```json
{
  "day": "YYYY-MM-DD",
  "attempted_sessions": ["10:00"],
  "submit_attempted": false,
  "submit_intent_at": "",
  "click_returned_at": "",
  "payment_stage_at": "",
  "terminal_status": null,
  "reason": "",
  "selected_region": "",
  "total": ""
}
```

终态：

- `payment_stage_reached`：页面已进入未支付支付阶段；停止当天全部后续任务，
  但仍应由用户在订单管理页核实订单。历史状态中的 `order_created` 保持兼容。
- `unknown`：停止当天全部后续任务。
- `halted_today`：登录、验证码、风控、配置或硬校验异常。
- `retryable_failure` 不写终态，但在 `attempted_sessions` 中记录本场已尝试。

## 11. 并发与重复保护

三层保护：

1. Windows 任务设置 `MultipleInstances=IgnoreNew`。
2. Python 使用操作系统级文件锁，同一时刻只允许一个 runner。
3. 当天状态文件记录已尝试场次和提交是否已发起。

不能在网络未知时依赖“页面看起来没变化”判断没有下单；提交标记必须先持久化。

## 12. 通知

使用独立 PushPlus：

- 成功：未支付订单已创建、场次、地域、金额、手机付款路径、60 分钟期限、
  自动续费后置检查。
- 明确失败：原因和是否有下一场。
- 结果未知：明确要求先查订单管理，不得重复下单。

PushPlus 默认最多重试 6 次，指数退避最大 15 秒。通知失败不改变订单状态。

## 15. 2026-10-27 10:00 事故

现象：

- 09:55 正常启动。
- 旧代码在 09:59:55 重载活动页。
- 10:00:12 仍未定位到目标卡，安全停止。
- `submit_attempted=false`，没有订单。
- PushPlus 同时连接重置，失败通知未送达。

已修复：

- 移除开抢边界重载。
- 浏览器预载从 T-10s 提前到 T-30s。
- 目标卡等待可延伸到本轮允许窗口结束。
- 目标卡缺失从“全天停止”改为“本场可重试”。
- 事件驱动监听替代每秒轮询。
- 配置弹窗、选项选中、跨域新页和提交结果改为事件/状态等待，移除关键路径固定
  0.3–0.5 秒 sleep。
- 点击前检查当前可见的售罄或资格提示，命中时不记录提交意图。
- 记录点击意图、点击返回、支付阶段三个阶段时间戳和全流程阶段耗时。
- 失败路径保存截图和 DOM。
- PushPlus 重试次数增加。
- 任务失败返回非零退出码。

| 商品约 1 秒售罄 | 即使本地很快，也可能在弹窗或订单请求前失去库存 |
| 配置 Schema 运行时变化 | 选择器或字段顺序可能不同 |
| 页面高并发加载 | 卡片、价格或弹窗可能延迟或失败 |
| 跨域弹窗被阻止 | 订单确认页可能无法打开 |
| 登录态过期 | 任务会在登录检查处停止 |
| 验证码/风控 | 脚本不得绕过，只能停止并通知 |
| 提交结果不确定 | 必须冻结当天流程并人工查订单 |
| Windows 锁屏/休眠 | 已做配置，但系统策略或硬件可能仍然阻止唤醒 |
| PushPlus 网络异常 | 订单可能成功但通知失败 |
| 用户活动资格 | 服务端可能在最后才拒绝 |

## 17. 建议学长重点评审

1. 在 1 秒售罄场景下，是否还有比 UI 自动化更可靠的合规路径。
2. 去掉 T-5 重载、保留 T-30 预载后，页面状态能否在开抢瞬间自行刷新。
3. 配置弹窗中默认可售地域优先是否合理，还是应保持固定地域。
4. `.submit-btn` 是否确实就是“生成未支付订单”的唯一 UI 边界。
5. 点击后 10 秒判定窗口是否太短或太长。
6. 结果未知时冻结当天全部场次是否过于保守。
7. Windows 锁屏状态下 Playwright/Edge 的实际可靠性。
8. 如何在不额外下单的前提下验证自动续费默认状态。
9. 是否应增加本地 Windows 通知，作为 PushPlus 失败时的非远程兜底。
10. 是否需要把“确认页控件快照”作为未来 UI 改版告警。

## 18. 结论

这套方案的重点不是“保证抢到”，而是：

- 使用真实已登录浏览器，不导出 Cookie。
- 用最少网络请求缩小热路径延迟。
- 严格核对商品、配置和金额。
- 最多创建一笔未支付订单。
- 绝不自动付款。
- 提交结果不明确时宁可停止，也不重复下单。
- 将未验证的 DOM 和自动续费状态转为运行时证据。

当前还缺少一次真实成功走到配置弹窗和订单确认页的实盘验证。15:00 的任务会同时承担真实抢购尝试和动态流程取证。

## 20. 当前直接接口实现（权威设计）

### 20.1 用户授权后的边界

用户明确允许在同一个已登录浏览器上下文中，复用当前活动页的 CSRF、请求头和动态
签名，直接调用当前活动接口。以下限制没有放宽：

- 单账号、单浏览器上下文、单实例锁。
- 只提交上海 `regionId=4`。
- 页面可从 14:55 开始观察，但直接 HTTP 下单只在 14:59:58.5–15:00:30 进行。
- 14:59:40 左右发送一次 `get-now` 完成连接预热；14:59:50 左右发送两次
  `get-now`，选择 RTT 最小的样本校时；此后直到首批下单不再发网络请求。
- 每批最多 10 个并发，批间等待 350–600ms 抖动；收到 408 后下一批延后 1.5 秒。
- 最多 200 次，取得订单标识后立即停止新增请求。
- 不用多账号或跨地域并发，不换地域补单。
- 每次提交前刷新页面签名；成功返回订单标识后立即停止新增提交。
- 不绕过登录、验证码、实名、排队、风控或限购。
- 不导出 Cookie，不保存 CSRF、动态签名或设备令牌。
- 绝不点击或调用支付动作。

### 20.4 结果判定

- `code=0` 且返回 `big_deal_no`、`deal_id` 或 `dealId`：创建未支付订单，
  记录 `order_created_at`，通知用户人工付款，并立即停止新增提交。
- 明确“尚未开始”或“已抢光/售罄”：没有进入订单生成，在硬截止时间前可以继续。
- `NOT-LOGINED`、`CSRF-ERROR`、验证码或不可重试的资格/风控错误：停止。
- `code=408`：记录原始响应，按已配置的短冷却后继续，直到硬截止时间或请求上限。
- 非 200、响应无法解析或未知错误码：记录脱敏证据；网络抖动可按有限策略重试，
  但在取得订单标识后不得继续。
