# 腾讯云活动接口限流调研

检索日期：2026-10-30（Asia/Shanghai）

## 结论摘要

1. `408 系统访问频率过快` 和 `1100205 当前系统繁忙` 都是 HTTP 200 响应里的业务码，
   不是普通的 HTTP 408/502。腾讯云没有在可检索到的公开官方文档中提供这两个活动
   内部码的完整定义。高置信度。
2. 公开实现中最接近成功的样本不是“从 14:57 持续刷三分钟”，而是先预热连接，
   在开抢前约 1.5–3 秒开始少量批次并发，并在 10 秒左右结束。中高置信度。
3. 2026-10-29 有一份公开成功日志：10 并发，约 20 次请求、5.4 秒内完成；同一批
   响应里同时出现 `408`、`1100205`、`1100110` 和一个成功订单。因此单条 `408`
   不能证明全部请求都失败，必须检查同一批的所有响应。中高置信度，来自项目作者
   发布的运行日志，不是腾讯云官方确认。
4. 另一个维护较久、使用纯 `requests` 的项目采用每轮 3 个地域并发、轮间
   350–600ms 抖动、`408` 后退避 1.5 秒。其文档认为连续大量 `408` 更像 IP 级限制，
   持续高频可能使限制延续到之后。中置信度，属于经验性描述。
5. 我们自己的 2026-10-30 实盘从 09:57 持续到 10:00:05，发送 483 次，其中 406 次
   `408`、56 次 `1100205`、19 次 `1101001`，没有订单。页面在 10:00:01.309
   才切换为“立即抢购”。这支持“提前长窗口高频会耗尽限流额度”的假设，但还不能
   单独证明限流究竟绑定 IP、账号、会话还是接口全局。高置信度事实，中置信度归因。
6. “独立 HTTP 比 UI 快 10 倍”在这个场景只减少了客户端渲染/点击开销，不能消除
   服务端排队和业务限流。公开成功样本与我们的失败样本都表明请求分布和限流状态
   比 HTTP 客户端的微秒级差异更重要。
7. 2026-10-30 15:00 的短批次实验直接验证了方案 A：14:59:40 预热、
   14:59:50 两次最低 RTT 校时、14:59:58.5 首批 10 并发。结果同一批中
   7 个 `408`、2 个 `1100110`、1 个成功订单；脚本首批后停止，只创建一笔
   上海 38 元未支付订单。高置信度，本地 state 与证据文件可复现。

## 证据

### 1. 实际成功与混合响应

项目：<https://github.com/djs-91/tencent-server-seckill>

成功日志：
<https://github.com/djs-91/tencent-server-seckill/issues/7>

固定版本源码：
<https://github.com/djs-91/tencent-server-seckill/blob/8724cc80da32237151af9cf524f3c4d679550d51/seckill.py>

公开日志中的关键事实：

```text
09:59:51  预热连接
09:59:52  预热返回 1101001（尚未开始）
09:59:57  正式开始，10 并发
10:00:03  同一批结果中同时出现：
          408
          1100205
          1100110
          下单成功
总计 20 次请求，5.4 秒
```

源码配置为 `CONCURRENCY=10`、`ROUND_INTERVAL_MS=20`、`DURATION_SEC=10`、
`ADVANCE_MS=-3000`。需要注意，它在每轮等待该批 10 个请求全部返回后才进入下一轮，
并不是理论上持续 500 req/s。成功日志实际只有约 20 次请求，说明这个样本的核心是
短时并发，而不是三分钟持续高频。

这条路仍有一个需要谨慎看待的地方：项目作者自己发布成功日志，日志中的订单号没有
腾讯云官方页面作为独立交叉验证。因此把它视为可信的开源复现线索，而不是官方事实。

### 2. 408 后主动退避的实现

项目：
<https://github.com/Allenalonel/tencentyun-seckill>

<https://github.com/Cec1c/tx-38sev-cheaper-robber>

固定版本源码：
<https://github.com/Allenalonel/tencentyun-seckill/blob/0595173bc494c98f7657acfbea4b200a0ca9da99/snap_up_server.py>

该项目使用：

- 开抢前 1.5 秒开始；
- 每轮同时请求 3 个地域；
- 默认 30 秒重试窗口；
- 轮间基础间隔 350ms，再加 0–250ms 随机抖动；
- 单请求超时 3 秒；
- 收到 `408` 后退避 1.5 秒；
- `1100205` 和 `1100110` 继续；
- `1101411` 表示已有未支付订单，立即停止。

项目说明还指出：

> 零延迟持续高频轮询可能在 5 秒内把 IP 送进限流状态；遇到连续 `408` 应先退避，
> 持续出现时应考虑出口网络，而不是继续增加并发。

这是维护者对实战经验的总结，错误码说明并非腾讯云官方文档，可信度按中等处理。

### 3. 低频也会触发 408 的公开问题

<https://github.com/CodeEmpower/txyun/issues/1>

提问者报告：只抢一个地域、每地域并发设为 2，仍然收到
`系统访问频率过快，请稍后再试`。Issue 目前没有公开解决方案。

这说明“请求量低就一定不会触发”不成立。可能的解释包括：

- 同一账号或 IP 此前已有高频历史；
- 活动接口使用比请求数更复杂的反刷评分；
- 请求缺少当前前端运行时自动生成的字段；
- 热点时段对所有请求随机丢弃或排队；
- 项目使用的参数、登录态或网络链路本身存在异常。

由于没有控制变量实验，不能从这条 Issue 单独确认原因。

### 4. 请求头与签名对比

项目：<https://github.com/KenSporger/tencent-cloud-38-seckill>

固定版本源码：
<https://github.com/KenSporger/tencent-cloud-38-seckill/blob/26932949301177e8cd1a814038ba7b47701433e6/scripts/lib.py>

该项目使用毫秒级 `nowTime` 校时，并用 `preview=1` 请求验证登录和参数。源码明确
指出 `query-seckill-by-date` 是公开接口，不能靠它判断登录态；真正判断登录态需要
调用 `do-goods` 的预览模式。

我们在 2026-10-30 捕获了一次真实浏览器 `preview=1` 请求，只记录请求头名称和值长度：

- 实际出现 `x-csrf-token`、`x-dss`、`x-rce-token`；
- 没有观察到额外的 `anti-brush` 请求头；
- 真实浏览器发出的这次 `preview=1` 同样返回 `408`。

这降低了“我们的独立 HTTP 客户端仅仅因为缺少隐藏 anti-brush 头而被单独拦截”的可能。
不过，TLS 指纹、HTTP/2 设置和浏览器会话历史仍可能参与未公开的风控评分，目前证据
不足以完全排除。

## 值得尝试的下一步

### 方案 A：短时批次并发，停止提前长窗口刷请求（推荐）

这是与公开成功样本最接近、同时仍遵守单账号、单地域、手动付款边界的方案：

1. 14:55 启动并完成登录、资格、活动和签名预检。
2. 14:59:50 左右只发送一次 `preview=1` 请求，用于预热连接并确认当前会话。
3. 14:59:58.5 左右发送第一批 10 个并发 `do-goods`。
4. 等待这一批全部返回，不要只看到单个 `408` 就停止。
5. 若没有成功，约 350–600ms 随机间隔后再发下一批。
6. 出现 `408` 时将下一轮延后约 1.5 秒；出现 `1100205` 可以继续；出现
   `1100110` 或 `1101411` 时停止新增请求并检查订单。
7. 最晚 15:00:30 停止，不在 14:57–14:59:57 之间持续泵请求。

关键变化是：

```text
旧策略：约 3 分钟持续高频，库存开放前已积累大量 408
新策略：约 2 秒预热 + 少量并发批次，把请求预算留给库存真正开放的时刻
```

### 方案 B：保留独立 HTTP，但只改变批次结构

当前 `http-api` 模式的传输本身已经验证可用。优先修改调度方式，而不是继续增加
HTTP 并发：

- 每批 5–10 个，不再单线程以固定 100ms 无限发送；
- 每批处理完再决定下一批；
- 成功后停止新增批次；
- 对每种业务码分别统计，不把混合响应粗暴归类为整场失败；
- 保留 `1101411` 的未支付订单硬停逻辑。

### 方案 C：如果连续 408，优先冷却而非换代理

公开项目中有“切换出口 IP”的经验，但同时存在账号、实名和活动公平性限制。
本项目不应使用代理池、多账号或自动绕过办法。可以验证的安全做法只有：

- 先在原网络冷却至少 1.5 秒；
- 若连续多轮仍全部是 `408`，停止本场；
- 用户可在自己控制的另一条合法网络（如手机热点）上重新做 `preview=1` 测试，
  但不应自动轮换 IP 规避限制。

### 方案 D：把预算转成确定性

如果目标只是尽快让项目上线，UCloud `2C2G / 4Mbps / 1000GB月流量 / 59.40元/年`
是目前已核实的确定性候选。继续研究腾讯云限流适合做实验，但不应成为部署的唯一阻塞。

## 不建议继续验证的方向

- 从开抢前数分钟持续猛发几千次请求；
- 多账号、多 IP、代理池或自动切换网络以规避限流；
- 收到 `1100110`/`1101411` 后继续提交；
- 把 HTTP 200 里的 `408` 当作网络故障并自动无限重试；
- 为了测试而反复创建真实未支付订单。

## 建议的 15:00 对照实验

只使用现有账号、上海地域和一个浏览器会话：

- 13 分钟内不调用 `do-goods`；
- T-10s 一次 `preview=1`；
- T-1.5s 开始第一批 10 并发；
- 批次间隔 350–600ms；
- 收到 `408` 后下一轮退避 1.5 秒；
- 30 秒硬停止；
- 保存每一种响应码的计数和同一批的完整响应，不记录凭据。

这项实验可以回答两个问题：

1. 先前失败是否主要因为提前三分钟耗尽了请求额度；
2. 短时批次内是否也可能像公开成功日志一样出现“408 + 成功”混合结果。

## 信息可信度

| 结论 | 可信度 | 原因 |
| --- | --- | --- |
| `408`、`1100205` 是 HTTP 200 内的业务码 | 高 | 本地实盘响应直接证明 |
| 单条 `408` 不代表同一批全部失败 | 高 | 本地多次并发与公开成功日志均出现混合响应 |
| 短时约 10 并发比持续三分钟高频更合理 | 中高 | 成功日志与退避型项目一致指向该策略 |
| 连续 `408` 可能是 IP 级限流 | 中 | 多个项目经验一致，但没有腾讯官方确认 |
| 独立 HTTP 天然比浏览器 fetch 更差 | 低 | 浏览器 `preview=1` 与独立 HTTP 均出现 408，证据不足以区分 |
| 更换代理 IP 可以解决 | 低且不建议 | 公开经验存在，但无法确认限流主体，也涉及规避平台控制 |
